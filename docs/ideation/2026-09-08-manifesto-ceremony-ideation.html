Grounding Context

Current State (Verified via bsk Screenshots)

Both pages were verified live against a running Docker instance (localhost:80) with demouser / DemoPass123. The screenshots confirm the code-level analysis — the pages are functionally complete but visually flat.

Sign Page
White background, no texture, no ceremony. Just: title → subtitle → member names with underline → signature pad canvas → confirm button. The ClassicTemplate ornaments (, ⚜) are not rendering — likely missing font. The 3-second timer gate has no visual feedback.
Preview Page
Document in a thin gray border rectangle. No corner decorations, no emblem, no dividers visible. Full-width dark "发布" button. No TOC sidebar (no trackable clauses). The certificate looks like a form, not a proclamation.

Key Codebase Findings

  • Sign page (ManifestoSignPage.vue): Nav-bar + ManifestoViewer + action area (SignaturePad + buttons) + FlowViewer stacked vertically. Background is plain #fff, padding is 16px. No animations.
  • Preview page (ManifestoPreviewPage.vue): Two-column with TOC sidebar. Scroll-to-publish pattern. Also plain white, no ceremony styling.
  • ClassicTemplate.vue: Has corner ornaments (☙), family crest (⚜), gold accents (#c9a84c), serif font (Noto Serif SC), ornamental dividers (◆) — the code has ceremony elements but they don't render visually in the browser (font/glyph issue).
  • ModernTemplate.vue: Clean/minimal with 3-dot accent, system sans-serif, blue primary accent. Less ceremonial by design.
  • SignaturePad.vue: Canvas-based drawing with velocity-based stroke width (thinner when faster). No calligraphy effect, no visual feedback on signing.
  • Template registry (templateRegistry.ts): Extensible — new templates can be added without modifying existing ones.
  • CSS variable system: Theme tokens in style.css with dark mode support via van-config-provider. Ceremony-themed tokens can cascade.

Design System (ui-ux-pro-max)

  • Product pattern: E-signature / Document Workflow → Trust & Authority + Minimalism
  • Color palette: Trust navy (#1E3A5F) + signature green (#16A34A) + neutral grey. Matches manifesto "formal commitment" use case.
  • Typography: EB Garamond + Lato — "Legal Professional" pairing. Serif for authority, sans for readability.
  • Animation: GSAP scroll reveal (power1.out, 300–400ms) for subtle progressive disclosure; power2.out staggered for standard reveals.

Frontend Constraints

  • Vue 3 + TypeScript + Vant 4, CSS variables + scoped styles
  • Dark mode required (CSS variable theming)
  • i18n required for all user-facing text
  • No new UI libraries; Iconify for icons
  • Mobile H5 primary (desktop secondary)
  • Snowflake IDs must be string type

1 Ceremonial Chamber — Immersive Full-Screen Mode
Axis: Ceremonial Atmosphere Confidence: 85% Complexity: Medium

Transform the sign page into an immersive, full-screen ceremony "room." When the user enters the sign page, the nav-bar fades out, the background transitions to a warm parchment tone (or deep navy in dark mode), and the manifesto document appears centered with a subtle drop shadow — like a physical document placed on a table. The rest of the app chrome (tab bar, status bar) dims or hides. The user is no longer in "an app page" — they are in a ceremony space. On the preview page, a similar treatment applies: the document is framed as a certificate, not a form preview.

Directional: Sign page transforms from "app page" to "ceremony room" — document centered, chrome dimmed, warm atmosphere.
Basis reasoned: The sign page currently uses a standard van-nav-bar with the app's default white background (ManifestoSignPage.vue:3-7, line 285: background: var(--bg-primary, #fff)). This signals "utility page" to the user. E-signature platforms like DocuSign use immersive signing experiences that remove all non-essential UI. The structural problem is that a family covenant deserves a different spatial contract than checking account balances.
Rationale The single biggest lever for perceived formality is the container, not the content. Moving from "a page in the app" to "a dedicated ceremony space" costs ~200 lines of CSS (overlay, transitions, hide/show logic) but fundamentally changes the user's mental model. This is the foundation that makes all other ceremony investments visible.
Downsides Hiding the nav-bar reduces discoverability of the back button — need a clear exit gesture (swipe-back or a subtle close icon). Must respect prefers-reduced-motion for the transition animation. The immersive mode should feel optional, not trapping.
2 Calligraphy Signature — Brush Pen Rendering
Axis: Signing Interaction Confidence: 80% Complexity: Medium

Replace the plain canvas signature pad with a calligraphy-style renderer. The SignaturePad already has velocity-based stroke width (SignaturePad.vue:102-107), but it maps to a uniform dark line. Upgrade it to simulate a brush pen: stroke width varies from thick (slow) to thin (fast), with a slight ink-bleed effect at direction changes. When the user lifts their finger, the signature "sets" with a subtle ink-spread animation. The clear button becomes "erase" with a wipe animation.

Directional: The same stroke path rendered as plain line vs. brush pen calligraphy — velocity determines width, direction changes create ink variation.
Basis direct: SignaturePad.vue:99-107 already computes velocity and maps it to stroke width (1.5–3px range), but the mapping is linear and narrow. The infrastructure for pressure simulation exists — it just needs a non-linear curve (exponential) and ink-bleed post-processing. The lineCap: 'round' and lineJoin: 'round' are already set.
Rationale In Japanese calligraphy (書道) and Chinese brush writing, the signature IS art — each stroke carries intention. Making the digital signature feel hand-crafted rather than machine-drawn is the single highest-impact change to the signing interaction. Users will feel their signature is "theirs" in a way a uniform line never achieves.
Downsides Requires canvas compositing knowledge for ink-bleed effect. Must test on low-end mobile devices — additional canvas operations cost GPU cycles. Dark mode needs careful contrast tuning for the ink color.
3 Living Family Crest — Dynamic Heraldry
Axis: Family Identity & Heritage Confidence: 75% Complexity: Medium

Generate a unique SVG family crest dynamically from the family's data: the family name (or first character), member count, and member roles (owner/child/member) determine the crest's composition. Display it prominently at the top of both the sign and preview pages — above the document title. Each time a new member signs, their initial is "added" to the crest's ring, making the crest a living record of the family's commitment. The crest uses the gold accent color (#c9a84c) from the existing ClassicTemplate palette.

Directional: Family crest auto-generated from member data — initials placed around the shield, family character at center. Grows as members sign.
Basis direct: ClassicTemplate.vue:12 already has a static .emblem-shield with ⚜ — it's a hardcoded emoji that may not render. The familyStore.members array (ManifestoSignPage.vue:181-183) provides all the data needed: member names, roles, and count. The crest can be computed as a pure function of this data.
Rationale A family crest is the universal symbol of lineage and shared identity across cultures. Making it dynamic (not a stock image) gives each family a unique emblem. The "living" aspect — members joining the crest as they sign — turns the document from static text into a growing family artifact. This directly leverages existing store data with no backend changes.
Downsides Generating aesthetically pleasing SVG layouts from arbitrary data is non-trivial — edge cases with 1 member vs. 8 members. Need a fallback for families without a clear "name" character. The crest should feel personal, not algorithmic.
4 Progressive Scroll Reveal — Document as Ceremony
Axis: Document Presentation Confidence: 82% Complexity: Low

Instead of the manifesto text appearing all at once, each paragraph fades in as the user scrolls — like a scroll being unfurled. The title appears first with a gentle scale-up, then the ornamental divider draws itself (CSS animation on the width), then each paragraph fades up as it enters the viewport. The effect uses GSAP ScrollTrigger or IntersectionObserver with power1.out easing at 300–400ms. Respect prefers-reduced-motion by showing all content immediately. This transforms the act of reading from passive scanning to active "receiving" of the family covenant.

Basis external: GSAP ScrollTrigger's subtle tier: gsap.from(el, { opacity: 0, y: 12, duration: 0.35, ease: 'power1.out' }) — the ui-ux-pro-max design system recommends this exact pattern for formal content. The ClassicTemplate already has the structural elements (divider, paragraphs) that benefit most from staggered reveal.
Rationale Sacred texts across traditions are revealed progressively — Torah scrolls are unrolled section by section, sutras are chanted verse by verse. The pacing IS the meaning. A family covenant deserves the same treatment: the user doesn't "see" the document, they "receive" it. This is also the lowest-complexity idea with high visual impact — pure CSS/JS animation, no structural changes.
Downsides Must handle prefers-reduced-motion gracefully. On very long manifestos, the staggered reveal could feel slow — need to cap the total animation time. The preview page's scroll-to-publish pattern already tracks scroll position, so the infrastructure partially exists.
5 Digital Wax Seal — Animated Signing Ritual
Axis: Signing Interaction Confidence: 72% Complexity: High

After the user draws their signature and taps "Confirm," instead of an instant toast notification, play a wax seal animation: a gold circle appears at the signature location, the user's initials are "pressed" into it with a stamp animation (scale down + slight rotation), then the seal "sets" with a subtle glow. The signature area transitions from "pending" to "sealed" with the member's name and a timestamp. This turns the confirmation from a UI event into a ceremonial moment — the digital equivalent of pressing a wax seal into a letter.

Directional: Three-stage ritual — sign → seal press → sealed document. The wax seal animation replaces the instant toast confirmation.
Basis cross-domain analogy: Historical wax seals (used since medieval times for authenticating documents) carry three properties that digital confirmations lack: physicality (the press), uniqueness (each seal is one-of-a-kind), and permanence (once set, it cannot be undone). The current showSuccessToast(t('manifesto.signSuccess')) (ManifestoSignPage.vue:231) is a generic app notification — it carries none of these qualities.
Rationale The moment of signing is the emotional climax of the entire manifesto flow. It currently resolves in 200ms with a toast. A wax seal animation extends that moment to 1.5–2 seconds of deliberate, satisfying interaction — the user watches their commitment become "real." This is the highest emotional ROI moment in the entire feature.
Downsides Highest complexity of all ideas — requires SVG animation sequencing, state management for the seal visual, and careful timing. Could feel slow if over-animated. Must be skippable for users who've signed before and just want to complete the flow quickly.
6 Signing Milestone Timeline — Integrated Flow
Axis: Flow Narrative Confidence: 78% Complexity: Low

Instead of the flow chart being a separate component at the bottom of the sign page (ManifestoFlowViewer), integrate the signing milestones directly into the document's signature area. Show a vertical timeline along the right edge of the document: each member's name appears with a status indicator (pending circle → signing pen icon → sealed checkmark). As members sign, their milestone animates from "awaiting" to "sealed" with a subtle glow pulse. The timeline becomes part of the document's visual identity — showing the family's collective commitment journey as a living record.

Basis direct: The ManifestoFlowViewer component and its node variants (FlowSigningNode, FlowPendingNode, FlowEffectiveNode) already compute all the flow state data. The useManifestoFlow composable provides memberStates, signingProgress, and flowState. The data layer is complete — only the presentation needs to move from a separate chart to an integrated timeline.
Rationale The current flow viewer is disconnected from the document — it sits below the action area like a status dashboard. By integrating the flow into the document's signature grid, the signing progress becomes part of the family story. Each signature is not just a status update; it's a chapter in the family's commitment narrative. This also simplifies the layout by removing a separate component.
Downsides Merging two components (flow viewer + signature grid) requires careful UI design to avoid clutter. The current flow viewer has rich state information (rejection, version updates, deadlines) that may not fit a simple timeline. May need to keep the full flow viewer for complex states while using the simplified timeline for the happy path.
7 Parchment & Ink Theme System — Visual Foundation
Axis: Ceremonial Atmosphere Confidence: 88% Complexity: Low

Establish a ceremony-specific CSS variable theme that all manifesto components share. Add tokens like --ceremony-parchment (#fdf6e3), --ceremony-ink (#1a1a2e), --ceremony-gold (#c9a84c), --ceremony-border (double-rule pattern), and --ceremony-shadow (warm drop shadow). Apply these to the ClassicTemplate (fixing the rendering issues), and make them available to any future ceremonial template. The theme auto-adapts for dark mode: parchment becomes deep navy, ink becomes warm white, gold stays gold. This is the visual foundation that makes every other ceremony idea cohesive.

Basis direct: The app already uses CSS variables for theming (frontend/apps/main/CLAUDE.md: --bg-primary, --card-bg, --text-primary). The ClassicTemplate hardcodes colors like #c9a84c and #0a0a0a (ClassicTemplate.vue:89-100) instead of using tokens — making them non-themeable. The van-config-provider already handles dark mode switching.
Rationale This is the lowest-complexity, highest-leverage idea. Every visual ceremony improvement (ornaments, textures, typography) needs a consistent color and style foundation. Without it, each feature adds ad-hoc styles that drift from each other. With it, every future template or component automatically participates in the ceremony aesthetic. It also fixes the existing ClassicTemplate rendering issues (hardcoded colors that don't adapt to dark mode, emoji glyphs that may not render).
Downsides Adding new CSS variables increases the theme surface — needs documentation. The parchment color may not work well in dark mode without a proper inversion strategy. Existing templates need to be migrated to use the new tokens (backward-compatible fallback values mitigate this).

Rejection Summary

# Idea Reason Rejected
1 Ambient Background Music Cross-domain analogy (wedding/tea ceremony) — rejected: mobile H5 auto-play restrictions make this unreliable; users in public spaces would find it jarring. Better suited as an opt-in "atmosphere" toggle in a future iteration.
2 Reading Confirmation Tracking (must-read-all-before-signing) Constraint-flip — rejected: adds friction to an already slow flow. The 3-second timer gate already provides a minimum reading pause; tracking paragraph-level reading is surveillance, not ceremony. Risk of user frustration.
3 Multi-Step Ceremony Sequence (Read→Affirm→Sign→Seal) Assumption-breaking — rejected: 4 steps is too many for mobile. The current single-page flow (read → sign → confirm) is the right granularity. The ceremony sequence idea's best elements (affirmation, seal) are absorbed into Ideas 1 and 5.
4 Family Oath Recitation (text-to-speech reading) Cross-domain analogy — rejected: TTS on mobile feels robotic, not ceremonial. The manifesto content is personal and varies per family — a recorded voice would undermine the intimacy. Out of scope for current frontend constraints.
5 Anniversary Date Stamp (show manifesto age) Leverage — rejected: meaningful only for existing manifestos. The primary use case is creation and first signing. Can be added later as a dashboard enhancement; not critical for the sign/preview page ceremony.
6 Dark Mode as Default Ceremony Constraint-flip — rejected: the app already supports dark mode via CSS variables. Forcing dark mode for ceremony would conflict with user theme preference. Better to enhance both light and dark with ceremony tokens (covered by Idea 7).
7 Member Portrait Avatars Pain & friction — rejected: the app doesn't currently store avatar images for family members. Would require backend changes to the user profile schema. Out of scope for a frontend-only ceremony improvement.
8 Template Ceremony Levels (encode ceremony intensity in templates) Assumption-breaking — rejected: premature abstraction. With only 2 templates, adding a "ceremony level" dimension is over-engineering. The template registry can be extended later when more templates exist.
