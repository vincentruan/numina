2. Important Findings

Finding 1: Web Push is ~85% complete, not starting from zero The backend notification domain is mature: 6 categories, 16 event types, 4 channels (telegram/email/feishu/webpush), multi-device subscription, retry with 410 cleanup, and scheduler integration. Phase 2 is completing and extending existing infrastructure — not building from scratch.
Finding 2: Prior Sept 2026 ideation already rejected full uni-app migration The prior ideation (53 days ago) evaluated 7 approaches and concluded: full uni-app migration costs 2-3 months for 3,621 Vant references + 546 browser API call sites, with uv-ui covering only ~70% of Vant. The recommended path was PWA + Capacitor. This new request revisits the same decision space with an emphasis on uni-app shell + web-view — a much thinner approach than full migration.
Finding 3: uni-app web-view is NOT the same as full uni-app migration The user's proposed approach (thin uni-app shell + web-view loading existing H5) is fundamentally different from the full migration rejected in Sept. It keeps all Vue/Vant/ECharts code running in WebView, using uni-app only as an Android packaging shell. This avoids the 3,621 Vant reference problem entirely.
Finding 4: Existing notification domain model is well-structured for extension The current NotificationChannel + NotificationSubscription + ReminderNotification model supports channel-agnostic dispatch. Adding a new "android_push" channel type follows the existing pattern without restructuring.
Finding 5: Self-hosted deployment is the primary constraint Numina deploys via Docker Compose on user-controlled infrastructure. Any solution requiring mandatory third-party cloud services (uniCloud, FCM-only) conflicts with the privacy-first positioning. Native push must be optional and replaceable.
Finding 6: PWA push is dead code — usePushSubscription never called The composable is fully implemented in both main and child apps, but no component ever imports or invokes it. Push subscription will never register until a Settings page or App.vue entry point calls it. This means the entire backend push infrastructure (VAPID, pywebpush, dispatcher, scheduler) is built and tested, but no real user has ever received a push notification from Numina.
Finding 7: Backend push has tests + push_service.py for real-time notifications tests/backend/test_web_push.py has 7 test cases covering subscription CRUD and send logic. services/notification/push_service.py has send_family_interaction_push() that bypasses the reminder system for real-time notifications. The backend is ready — it's the frontend trigger that's missing.

Option Analysis

A. Capacitor Shell (Recommended Primary)

Capacitor wraps the existing H5 in a native Android WebView. It's the thinnest possible shell: ~10MB runtime, zero changes to existing Vue/Vant code, Cookie-based auth works transparently, and it supports native plugins for push (FCM), file access, and deep links.

  • Killer advantage: Zero business code changes. The same H5 runs in Capacitor WebView exactly as in Chrome.
  • Killer disadvantage: FCM doesn't work in China. For CN push, you'd need a custom plugin or fallback.

B. uni-app Shell + web-view (Recommended if CN Push is critical)

A thin uni-app project that does NOT rewrite any UI — it just loads the existing Numina H5 in a <web-view> component. The uni-app layer provides: Android packaging, uni-push 2.0 (multi-vendor CN push), and a JS bridge for native capabilities.

  • Killer advantage: uni-push 2.0 gives excellent CN delivery via Huawei/Xiaomi/OPPO/vivo vendor channels — something no other option achieves.
  • Killer disadvantage: uni-push 2.0 requires uniCloud function as relay → data flows through DCloud/个推 third-party servers. This is the primary privacy concern.
  • Key risk: web-view has subtle behavioral differences from Chrome (Cookie handling, file upload, back button, SSE streaming). Each needs testing.

C. Full uni-app Migration

Rewriting the entire frontend in uni-app. This was comprehensively evaluated and rejected in the Sept 2026 ideation: 3,621 Vant references, 546 browser API calls, uv-ui ~70% coverage, ECharts→ucharts migration, WebAuthn has no equivalent.

Not recommended. 2-3 months of work for marginal benefit. The use case (family asset dashboard) does not need deep native UI.

D. TWA / PWA

Trusted Web Activity wraps the PWA for Play Store listing. Or just rely on "Add to Home Screen" PWA install.

  • Killer advantage: Near-zero effort. PWA already works.
  • Killer disadvantage: No background push on iOS (iOS 16.4+ supports it but with severe limitations). No CN push at all. No control over WebView behavior. Cannot work on LAN HTTP (SW requires HTTPS).

4. Recommendation

Primary Recommendation: Capacitor Shell (Option A)

For Phase 1: Use Capacitor to wrap the existing Numina H5 as an Android App. This gives you:

  • A real installable APK with zero business code changes
  • Cookie-based auth works transparently
  • Native file picker, camera, download via Capacitor plugins
  • Intent filter deep links
  • ~1-2 weeks to first APK
  • Zero third-party cloud dependency

For Phase 2 push: Keep existing Web Push (VAPID) for PWA. Add Capacitor FCM plugin for overseas Android users. For CN users, the PWA Web Push path remains the primary notification channel (works on Android Chrome, Samsung Internet, etc.).

Privacy impact: Minimal. Capacitor adds a native runtime layer but introduces no mandatory cloud dependency. FCM is optional and can be disabled.

Fallback / Alternative: uni-app Shell + web-view (Option B)

Choose this ONLY if CN Android push delivery is a hard requirement.

uni-push 2.0 is the only realistic way to achieve reliable push delivery on Chinese Android devices (Huawei/Xiaomi/OPPO/vivo/荣耀). No other option provides vendor-channel integration without building individual SDK integrations.

But you must accept:

  • Push metadata flows through DCloud/个推 servers (see §11 Privacy Analysis)
  • uni-push requires a uniCloud function as relay — even though your business server is self-hosted
  • The native push path becomes: FastAPI → HTTP → uniCloud → 个推 → vendor channel → device
  • This must be an opt-in feature, not a default

Why not uni-app shell as primary?

  1. Privacy-first conflict: uni-push's mandatory uniCloud relay contradicts Numina's self-hosted positioning. Capacitor's FCM is at least optional and Google-only.
  2. WebView behavioral risk: uni-app's web-view has known quirks with SSE streaming, Cookie SameSite handling, and file upload that need prototype validation. Capacitor's WebView is closer to stock Chrome.
  3. Community/ecosystem: Capacitor has a larger ecosystem, better documentation, and more active maintenance for the "thin shell" use case.
  4. CN push reality: Even with uni-push, users on self-hosted instances behind LAN HTTP won't receive push (no network reachability). The push problem for self-hosted Numina is more about server reachability than push provider choice.

5.2 Server URL Configuration

First launch flow:

  1. App opens → shows Server URL setup page (native Vue, not WebView)
  2. User enters URL: https://numina.example.com or http://192.168.1.100:80
  3. App validates: GET /api/health → checks response
  4. URL saved to SharedPreferences via Capacitor Preferences plugin
  5. WebView loads {serverUrl}/

Multi-instance support: One APK can connect to any self-hosted instance. The server URL is per-installation, not per-user. Different users on different instances get different configurations. This is a feature, not a limitation — it matches Numina's self-hosted model.

5.3 HTTPS Policy

ScenarioPolicyRationale
Production (public domain) HTTPS required Cookie security, PWA, Web Push all require it
LAN HTTP (192.168.x.x / .local) Allowed with warning Self-hosted families on home network. Show "Advanced mode" toggle + security warning
Self-signed cert Allowed with explicit trust Android WebView needs WebViewClient.onReceivedSslError override — prompt user once, store fingerprint
Android cleartext HTTP: Android 9+ blocks cleartext by default. The Capacitor shell must set android:usesCleartextTraffic="true" in AndroidManifest.xml. This is acceptable for a self-hosted app but should be gated behind an "Advanced mode" setting that the user explicitly enables.

5.4 Auth / Cookie Handling

Capacitor's WebView shares the same Cookie jar as the native Android app. Numina's existing httpOnly Cookie JWT auth works transparently — no changes needed.

  • Same-origin Cookies: automatic when WebView loads the server URL
  • Cross-origin: Capacitor's server URL is the origin, so Cookies are same-origin
  • Cookie persistence: Android WebView persists Cookies across app restarts
  • Logout: calling the existing /auth/logout endpoint clears the Cookie as usual

5.5 WebView Loading Strategy

Single WebView approach: One <web-view> loads the server root URL. Navigation between main and child happens via URL:

  • Main app: {serverUrl}/
  • Child app: {serverUrl}/child/

One APK or two? One APK. A single Android app with a role-based entry point. After login, the app detects the user's role (owner/parent/child) and loads the appropriate H5 path. This matches Numina's existing role-based access control.

5.6 Android Back Button ↔ Vue Router

The Capacitor shell registers a back button handler that:

  1. Sends a goBack message to the H5 via JS bridge
  2. H5 calls router.back()
  3. If router.currentRoute is at the root (tab bar home), the bridge responds "at root"
  4. Capacitor calls App.exitApp() or shows "press back again to exit" toast

The native handler extracts the path and sends it to the H5 via bridge → Vue Router navigates.

5.10 Version Mismatch Handling

The shell should NOT cache any business HTML/JS/CSS. Everything loads from the server. The only "local" content is the setup page and bridge code. This eliminates version mismatch for business logic.

Bridge protocol version: The shell exposes a bridgeVersion via JS. The H5 can check it and degrade gracefully if the shell is too old for a requested feature.

5.11 Offline / Network Error UX

When the WebView can't reach the server:

  1. Capacitor detects network error via WebViewClient.onReceivedError
  2. Show a native error page with: "Cannot connect to {serverUrl}" + retry button
  3. If server URL is unreachable, offer "Change server URL" option
  4. No local cache of business pages — the app is a thin client

6.3 Recommended Push Strategy

Phase 2a: Complete PWA Web Push (existing infrastructure, ~1 week) Fix the notificationclick bug, add child app subscription, add pushsubscriptionchange handler, add preference UI. This alone gives reliable push for all Android Chrome + desktop browser users.
Phase 2b: Add FCM for Capacitor Android (optional, ~2 weeks) For users who install the Capacitor Android app AND want background push. FCM works for overseas users. CN users behind GFW won't receive FCM — they fall back to PWA Web Push (which works on Android Chrome regardless of GFW, because it uses standard HTTPS).
Phase 2c (Deferred): uni-push 2.0 only if CN native push is a hard requirement This introduces DCloud/个推 dependency. Make it a configurable provider, not a default. See §11 for full privacy analysis.

6.6 Dedup / Collapse Strategy

  • Tag/collapse: Same reminder_type + family_id → same notification tag → Android auto-collapses
  • Idempotency: ensure_reminder() already deduplicates by (family_id, reminder_type, asset_id, status=active)
  • Rate limiting: check_reminder_dedup() provides 1-hour dedup window for AI task notifications
  • Retry with backoff: _retry_failed_notifications() retries up to 3 times via scheduler

11. Privacy & Self-hosting Impact

11.1 uni-push 2.0 Privacy Analysis

uni-push 2.0 data flow: 
FastAPI (self-hosted)
  → HTTP POST to uniCloud function (DCloud cloud, hosted in China)
    → Contains: notification title, body, target CID, app_id
    → DCloud server processes the request
      → Forwards to 个推 (GeTui) push service
        → 个推 routes to vendor channel (Huawei/Xiaomi/OPPO/vivo)
          → Device receives notification

What leaves self-hosted environment:

  • Notification title and body text (even with "opaque" privacy, the type of notification is visible)
  • Target device CID (client ID)
  • App ID (identifies your app)
  • Timestamp of each push
  • User's approximate push frequency pattern

What does NOT leave:

  • Asset amounts, balances, financial data (if opaque privacy level is used)
  • User credentials
  • Family data, member names

Privacy policy impact: Must disclose that push notifications are routed through DCloud/个推, with metadata about notification type and timing. Users who want zero third-party dependency must use PWA Web Push (which goes through the browser's push service — Google for Chrome, Mozilla for Firefox, etc. — but that's an inherent Web property, not a Numina choice).

11.2 FCM Privacy Analysis

FCM has a simpler data path:

FastAPI → HTTPS POST to fcm.googleapis.com → Google FCM → Device
  • Google sees: notification payload, target device token, timestamp
  • Google does NOT see: server IP (it's a standard API call)
  • For opaque notifications, Google only sees "Numina sent a notification" — no financial data
  • Blocked in China — not accessible behind GFW

11.3 Web Push Privacy Analysis

Web Push (VAPID) data path:

FastAPI → HTTPS POST to push service (e.g., updates.push.mozilla.org, fcm.googleapis.com for Chrome) → Device SW
  • Push service sees: encrypted payload (only the device SW can decrypt with p256dh/auth keys)
  • VAPID ensures only your server can push to your subscribers
  • Push service sees metadata: endpoint URL, timing, payload size
  • This is inherent to Web Push standard — not specific to Numina
  • Works everywhere HTTPS works — including China (no GFW issue)

11.4 Recommendation

  1. Default: Web Push only. Zero third-party dependency beyond the browser vendor's push service (which is unavoidable for any web app).
  2. Optional FCM: For Capacitor Android users who want more reliable background push. Can be disabled in settings.
  3. Deferred uni-push: Only if CN native push delivery is proven to be a critical user need. Make it a configurable provider, opt-in per installation.
  4. Always opaque by default. No financial data in push payloads regardless of provider.

17. Things I Would NOT Do

🚫 Do Not Rewrite Existing Frontend in uni-app

The Sept 2026 ideation already concluded this: 3,621 Vant references, 546 browser APIs, 2-3 months of work for marginal benefit. The thin-shell approach (Capacitor or uni-app web-view) correctly avoids this trap.

🚫 Do Not Force PWA Through uni-push WebSocket

The existing Web Push (VAPID) implementation is standards-based, works globally, and has zero third-party dependency. Replacing it with uni-push WebSocket would: (a) break all existing PWA users, (b) introduce DCloud dependency for web users, (c) solve a problem that doesn't exist. Keep PWA on Web Push.

🚫 Do Not Make uni-push / DCloud a Default Dependency

uni-push 2.0 requires uniCloud function relay → data flows through DCloud/个推. This contradicts Numina's privacy-first positioning. If used at all, it must be: (a) opt-in per installation, (b) behind a clear privacy disclosure, (c) replaceable via provider abstraction.

🚫 Do Not Build a Parallel Notification System

The existing notification domain (registry → dispatcher → sender → channels) is well-architected. Don't build a separate "push system" — extend the existing one with new providers (FCM, etc.) that plug into the same dispatch flow.

🚫 Do Not Enable Cleartext HTTP Globally

Android 9+ blocks cleartext by default for good reason. For self-hosted LAN scenarios, gate it behind "Advanced mode" with explicit user opt-in. Don't weaken security for all users to accommodate edge cases.

🚫 Do Not Put Financial Data in Push Payloads

Lock screen notifications are visible to anyone near the phone. Default privacy level = opaque. "Your Numina has a new notification" — never "Your credit card has ¥37,821.24 unpaid." Detailed content loads only after authentication inside the app.

🚫 Do Not Add a Message Queue (Yet)

The existing scheduler worker + APScheduler + retry pattern handles notification dispatch well. Don't introduce RabbitMQ/Kafka/Celery for push delivery unless volume demands it (it doesn't for family-scale usage). Redis Streams already handles cross-process events.

🚫 Do Not Support iOS in Phase 1

Capacitor supports iOS, but the setup is different (Xcode, Apple Developer account). Phase 1 focuses on Android. iOS can be added in a future phase with minimal additional work since the Capacitor shell is cross-platform.

🚫 Do Not Migrate Existing push_subscriptions Table Yet

The existing push_subscriptions table works for PWA. Don't merge it into device_registrations as part of Phase 1. Keep it stable. The migration can happen in Phase 2b when device registration is needed for FCM.

🚫 Do Not Use TWA as the Primary Android Strategy

TWA requires Digital Asset Links verification (domain ownership) and only works for Play Store distribution. It provides no native capabilities. For self-hosted Numina where users deploy on different domains, TWA's domain verification becomes a per-deployment burden. Capacitor shell is strictly more flexible.

Summary: Use Capacitor as a thin Android shell (Phase 1, ~2 weeks). Complete existing PWA Web Push (Phase 2a, ~1 week). Add optional FCM for Capacitor Android (Phase 2b, ~2 weeks). Keep uni-push as a deferred, opt-in option only if CN native push is proven critical. Maintain privacy-first by defaulting to opaque push payloads and zero mandatory third-party dependencies.
