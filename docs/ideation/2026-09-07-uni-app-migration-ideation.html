Grounding Context

Numina 当前有两套 Vue 3 + Vant 4 + TypeScript 前端应用，通过 pnpm workspace 组织，共享 @numina/auth、@numina/math、@numina/assets 三个包。主要服务手机端 H5 访问，现评估使用 uni-app 或替代方案扩展至 Android 原生 + PWA。

当前技术栈

  • Vue 3.5 + TypeScript 5.9 + Vite 8
  • Vant 4.9 (auto-import via unplugin)
  • Pinia 状态管理, vue-router 4
  • ECharts 6, vue-echarts 8
  • vue-i18n, axios, nprogress

鉴权架构

  • httpOnly Cookie 鉴权 (非 localStorage token)
  • 设备指纹 + ETag 可信设备机制
  • localStorage 仅缓存用户 profile
  • 2-step 登录 + WebAuthn passkey
  • 子应用通过独立 SPA 入口 (/child/)

关键依赖风险

  • Vant 4 — 3,621 处引用，36 个文件，Web-only
  • html2canvas/jspdf — DOM-only，原生端不可用
  • WebAuthn — 无 uni-app 等价 API
  • cropperjs/shiki/vuedraggable — DOM 依赖
  • ECharts — 有 ucharts 替代方案

uni-app 能力

  • ✅ Vue 3 + Composition API + <script setup>
  • ✅ Pinia 状态管理支持
  • ✅ H5 模式输出 Web 应用
  • ✅ App 模式输出 iOS/Android 原生
  • ❌ 不支持 Vant 4 (DOM 组件)
  • ❌ 路由系统不同 (pages.json vs vue-router)
  • ⚠️ PWA 支持有限 (非一等公民)

1. Capacitor + PWA 双轨方案
工程结构与复用策略 Confidence 90% Complexity Medium
使用 Capacitor 将现有 Vue 3 + Vant 4 H5 应用包装为 Android 原生应用，同时为 H5 添加 PWA 支持（Service Worker + manifest.json）。保持现有代码库不变，一次投入获得 Android App + PWA + H5 三端覆盖。
external: Rationale

Capacitor 是 Ionic 团队维护的成熟方案，专为"将 Web 应用打包为原生应用"设计。与 Cordova 相比更轻量，原生插件生态丰富。关键优势：现有 Vue 3 + Vant 4 代码零修改即可运行在 Android WebView 中。Cookie 鉴权在 WebView 中正常工作，后端无需任何改动。

Downsides

Android 端实际运行在 WebView 中，性能不如真原生应用（但对家庭资产仪表盘类应用影响极小）。需要额外添加 ~10MB 的 Capacitor 运行时。App 内无法使用 Vant 之外的原生 UI 组件（但也不需要）。

2. PWA 优先渐进路线
多平台能力覆盖 Confidence 85% Complexity Low
先为现有 H5 添加 PWA 能力（Service Worker 离线缓存、manifest.json 可安装、推送通知），获得"类原生"体验。后续再根据实际需求决定是否添加 Capacitor 打包 Android。这是最小成本、最高确定性的第一步。
reasoned: Rationale

用户的核心需求是"手机端更好的体验"，PWA 已经可以满足：可添加到主屏幕、离线可用、推送通知、全屏运行无浏览器 UI。在大多数家庭资产管理场景中，PWA 与原生 app 的体验差距极小。而成本仅为添加 vite-plugin-pwa + 配置 Service Worker 策略，约 1-2 天工作量。

Downsides

iOS 上 PWA 能力受限（推送通知 iOS 16.4+ 才支持，无 NFC/蓝牙等原生 API）。Android 浏览器兼容性极好但部分用户可能不知道"添加到主屏幕"功能。无法上架 Google Play（除非配合 TWA）。

3. 共享核心 + 平台外壳架构
工程结构与复用策略 Confidence 75% Complexity High
将现有共享包（@numina/auth、@numina/math、API 层、composables）保持为平台无关核心，Web 端保持 Vue 3 + Vant 4，Android 端用 uni-app + uni-ui 构建独立 UI。通过 workspace 共享业务逻辑，UI 层各自独立。
reasoned: Rationale

这是"既保留现有 H5 投资，又获得 uni-app 原生能力"的折中方案。@numina/math（纯函数）和 @numina/auth（已解耦 HTTP 注入）可以直接在 uni-app 中复用。API 层的 axios 调用替换为 uni.request 即可。工作量主要在 UI 重写，但业务逻辑和鉴权完整复用。

Downsides

维护两套 UI 代码（Web + uni-app），每个页面需要实现两次。新功能开发成本增加 ~40%。需要建立平台适配层的抽象（如 uni-or-axios HTTP wrapper），增加架构复杂度。Child app 跨 SPA 导航需要重新设计。

4. TWA (Trusted Web Activity) 封装
多平台能力覆盖 Confidence 70% Complexity Low
如果先做好了 PWA，可以用 TWA 将 PWA 封装为 Android 应用并上架 Google Play。TWA 是 Chrome 提供的机制，将符合 PWA 标准的 Web 应用以全屏方式运行在 Chrome Custom Tab 中，验证 Digital Asset Links 后无浏览器 UI。
external: Rationale

TWA 是 Google 官方推荐的"Web 应用上架 Play Store"方案。相比 Capacitor 更轻量（无额外运行时），性能更好（直接使用 Chrome 引擎）。Bubblewrap CLI 可一键生成 TWA 项目。前提条件是 PWA 必须通过 Lighthouse 审计。

Downsides

要求设备上安装 Chrome 72+（Android 上覆盖率极高）。需要域名验证（Digital Asset Links）。如果 PWA 不达标，TWA 会回退显示浏览器导航栏。本质仍是 WebView，与 Capacitor 方案效果类似但更受限。

5. 放弃原生 app，专注 H5 + PWA 优化
多平台能力覆盖 Confidence 65% Complexity Low
重新审视"需要 Android 原生 app"的前提假设。对于家庭资产可视化场景，H5 + PWA 可能已经足够好。将精力投入到 H5 体验优化（离线、推送、性能、动画）而非跨平台迁移，避免 3,600+ Vant 组件的重写成本。
reasoned: Rationale

Numina 的核心场景是家庭资产查看和管理，不涉及相机、蓝牙、NFC 等强原生能力需求。用户"想要 Android app"的真实需求可能是"更好的手机体验"——这恰好是 PWA 的甜区。3,621 处 Vant 引用 + 546 处浏览器 API 的迁移成本极高，投入产出比可能不如直接优化 H5。

Downsides

无法满足"在应用商店下载"的用户心理预期。某些企业场景可能需要原生 app 的管控能力。如果未来需要小程序（微信/支付宝），这个方案无法覆盖。

6. Child app 先行 uni-app 试点
UI 组件库兼容性 Confidence 60% Complexity Medium
先用儿童端（child app）做 uni-app 试点：14 个路由，更少的依赖，更简单的 UI。验证 uni-app + Vue 3 的可行性、Vant → uni-ui 的迁移模式、以及共享包（@numina/auth, @numina/math）在 uni-app 中的复用情况。试点成功后再迁移 main app。
direct: Rationale

Child app 复杂度远低于 main app：14 路由 vs 55+ 路由，无 ECharts/jspdf/html2canvas 等重型依赖，UI 更简单（clay.css 风格）。是验证 uni-app 迁移路径的理想试验田。试点结果将决定 main app 是否值得全量迁移。

Downsides

即使 child app 试点成功，main app 的迁移成本仍然是大头（3,600+ Vant 引用）。可能陷入"两套 UI 维护"的长期成本。Child app 使用了 WebAuthn passkey（uni-app 无等价 API），仍需特殊处理。

7. uni-app + uv-ui 完全迁移
UI 组件库兼容性 Confidence 40% Complexity Very High
将两个前端 app 完全迁移到 uni-app，使用 uv-ui（Vant 风格的 uni-app 组件库）替代 Vant 4，pages.json 替代 vue-router，uni.request 替代 axios。获得 Android + iOS + H5 + 小程序全平台覆盖。
direct: Rationale

这是用户最初提议的方案。uv-ui 提供了类似 Vant 的 API 设计，理论上可以降低组件替换成本。uni-app 的 H5 模式理论上可以替代现有 Vite 构建。全平台覆盖（包括微信小程序）是长期价值。

Downsides

成本极高：3,621 处 Vant 引用需要手动迁移（uv-ui API 不完全兼容），55+ 路由重写为 pages.json 格式，605 处 :deep() 选择器需重新验证，ECharts → ucharts、jspdf → 服务端 PDF、html2canvas → uni.canvasToTempFilePath 均需重写。WebAuthn 无替代方案。估计工作量：2-3 个月全职开发。且 H5 输出与现有 Vite 构建行为不完全一致，可能引入回归。

关键问题回答

Q1: Vue 3 + Vant 4 能否无缝切换到 uni-app？

  • 不能无缝切换。Vant 4 是纯 Web 组件库，依赖 DOM API，无法在 uni-app 的 App（原生）模式运行。
  • Vue 3 本身（Composition API、<script setup>、Pinia）在 uni-app 中完全支持。
  • uv-ui 提供类 Vant API 但覆盖度不足（约 70% 组件可映射），高级用法（slot、事件、动画）需逐个适配。
  • 迁移成本主导因素：3,621 处 Vant 引用、605 处 :deep() 覆盖、55+ 路由重写。

Q2: 新增支持后，是多个前端工程还是一个？

  • 推荐方案：保持当前 pnpm workspace 结构 + 新增一个 uni-app app。
  • 如果走 Capacitor 路线：不新增工程，现有 main app 直接打包为 Android。
  • 如果走 uni-app 路线：在 frontend/apps/ 下新增 native/ 作为 uni-app 工程，main 和 child 保持原样作为 H5。
  • 共享包（@numina/auth, @numina/math）可直接被 uni-app 工程引用（纯逻辑部分）。

Q3: 后端是否需要调整？鉴权方式？

  • 后端基本零修改。当前使用 httpOnly Cookie 鉴权，在 Capacitor WebView 和 uni-app H5 模式中都正常工作。
  • uni-app App 模式需要配置 uni.request 的 withCredentials: true 以携带 Cookie。
  • 设备指纹（ETag-based）在原生环境中需要适配：WebView 的 Cookie jar 行为与浏览器略有差异。
  • 如果需要原生推送通知：后端需对接 uni-app 的 UniPush 或 FCM，新增推送通道。
  • WebAuthn passkey 登录在原生端无替代方案，需要 fallback 到密码 + 2FA。

Q4: PWA 是否被 uni-app 覆盖？

  • uni-app 的 PWA 支持有限，不是其一等公民能力。H5 模式可输出 Web 应用，但 Service Worker 和 manifest.json 需要手动配置。
  • 如果 PWA 是核心需求，建议在现有 Vite 构建上直接添加（vite-plugin-pwa），这比 uni-app 的 PWA 支持更成熟。
  • Capacitor + PWA 组合 > uni-app 的 PWA 能力。前者 Service Worker 完整可控，后者需要处理 uni-app 构建流水线的兼容性问题。

Rejection Summary

# Idea Reason Rejected
1 Codemods 自动化 Vant → uni-ui 转换 API 差异过大（事件名、slot 结构、CSS 变量），无法可靠自动化
2 Electron 桌面类比方案 移动端场景与桌面端差异大，Tauri Mobile 尚未成熟
3 微前端模式（qiankun/single-spa） 过度工程化，Numina 不需要多团队并行开发的架构
4 Flutter 重写 完全不同的技术栈，放弃全部 Vue 投资，成本远超收益
5 NativeScript + Vue 社区萎缩，Vue 3 支持不完整，不如 Capacitor 成熟
6 React Native 重写 放弃 Vue 投资，学习成本曲线陡峭，不适合当前团队
7 localStorage → uni.storage 自动映射层 太细节，不是独立方向；属于具体实现步骤而非策略
8 去掉"两个 app 必须共享"的约束 不可行 — main 和 child 的用户群和功能紧密关联
9 uni-app 目标场景不匹配 是判断不是可执行 idea，已融入 #7 的 downside 分析
10 零预算 PWA only 与 Idea #2 (PWA 优先渐进路线) 重复
11 去掉"必须 uni-app"约束评估所有方案 与 Idea #1 (Capacitor) 重复 — 该 idea 本身就是替代方案
12 平台适配器模式 (抽象 uni/axios 等) 与 Idea #3 (共享核心 + 平台外壳) 重复，已合并
