Grounding Context

Numina is a privacy-first, self-hosted family asset visualization and management system. Backend: Python 3.12+ FastAPI + SQLAlchemy + Alembic. Frontend: Vue 3 + Vant 4 + Pinia. FinanceHubPage uses van-tabs with 4 tabs: assets, liabilities, wishes, rentals.

Key architecture: All financial entities are family-scoped via user_id + family_id. Money fields are Numeric(18,2) in DB, Decimal in Python, str on wire (SnowflakeBase). Strict family isolation — no cross-family access.

Existing precedents: RentalContract (date-range + status lifecycle + soft-delete, free-text counterparty for external parties), CoinTransaction (double-entry ledger for child economy), Wish (status lifecycle: pending/realized/cancelled, savings log with derived cache), PaymentRecord (liability repayment history), AssetSnapshot (daily net-worth with extensible JSON breakdown).

Key gaps: No expense ledger (only coin transactions and rental cash flow). No bill-splitting. No trip/booking management. No annual/periodic reporting (only daily snapshots). Liability categories are hardcoded (mortgage/car_loan/credit_card/personal_loan/other).

Leverage points: Multi-currency (Currency + ExchangeRate models), AI agent system (DeerFlow-based with import-parse skill for receipt vision), scheduler worker, dashboard narrative system.

#1 Wish→Trip Graduation Pipeline trip-planning

Extend the existing complete_wish flow so that when a wish with travel category is marked "realized", it offers to create a Trip entity pre-populated with the wish's expected_price as budget and saved_amount as initial funding. The wish's savings ledger (WishSavingsLog) carries over as the trip's funding history, preserving financial context from aspiration to execution.

Basis
direct: complete_wish docstring at wish.py:145 explicitly mentions "travel" as canonical use case. Wish.saved_amount is derived cache of WishSavingsLog. Verified: sound.
Rationale
Families already use wishes to track travel intentions with budgets and savings. When it's time to book, they re-enter everything into a separate system. This eliminates that boundary.
Downsides
Tight coupling between Wish and Trip lifecycle. If wish semantics change, trip graduation may break. Requires careful FK design (wish_id on Trip).
Confidence: 90% Complexity: Low
#2 Ephemeral Cross-Family SplitGroup via Invite Token bill-splitting

Create a SplitGroup entity with a 6-character invite code (mirroring Family.invite_code). External participants (friends, other families) join via the code and receive a scoped view of only the group's expenses — they cannot see the host family's assets, liabilities, or any data outside the group. The group is scoped to a single trip and expires when the trip closes. External participants are stored as free-text names (like RentalContract.counterparty), not full User records, preserving family isolation.

Basis
direct: Family.invite_code at family.py:15 is a proven 6-char token pattern. RentalContract.counterparty at rental_contract.py:33 handles external parties as free-text. Cross-family isolation is hard-enforced (test_assets.py:189). Verified: sound.
Rationale
The user explicitly wants bill-splitting with other families/friends, but cross-family access is architecturally rejected. The invite-code pattern is the minimum-viable bridge: proven UX, keeps family isolation intact, avoids building a full multi-tenant identity system.
Downsides
Free-text participants mean no authentication for external users — they can't independently verify expenses. Settlement requires trust. May need a "guest account" evolution path later.
Confidence: 88% Complexity: Medium
#3 Unified Double-Entry Expense Ledger expense-tracking

Generalize the CoinTransaction double-entry pattern from the child economy into a family-scoped expense ledger. Each travel expense creates two entries: a debit against a funding source (checking account, credit card) and a credit to an expense category. This reuses the existing double-entry infrastructure with SELECT ... FOR UPDATE locking, ensuring every expense has a verifiable source, split amounts balance automatically, and the audit trail exists for free. Trip expenses become one use case of the ledger, not a separate model — the same ledger later serves rental expenses, daily spending, etc.

Basis
direct: coin_transactions.py:51-90 has double-entry with concurrent-spend protection via SELECT FOR UPDATE. WishSavingsLog confirms the "source of truth = log, derived cache on parent" pattern. Verified: sound.
Rationale
A single-entry expense table is trivial to build but creates reconciliation nightmares when bill-splitting enters the picture. Double-entry from day one means the ledger compounds across modules — trip expenses today, rental expenses tomorrow, daily spending later.
Downsides
Higher initial complexity than a simple expense table. The debit/credit mental model may confuse non-technical family members. Needs careful UI design to abstract the double-entry from users.
Confidence: 85% Complexity: Medium
#4 Rental Cash Flow Mirror — Travel Float in Net Worth liability-and-stats

Mirror the rental cash flow integration pattern: add a travel_float metric to OverviewResponse showing the net unpaid travel expense balance. When a family pays for flights/hotels upfront but hasn't traveled yet, this is a "prepaid travel asset" (positive). When they've traveled but haven't settled group bills, this is "travel debt" (negative). The balance flows into net worth, making travel financially visible in the same way rental cash flow is today. Zero new aggregation infrastructure — add travel to the existing overview computation loop.

Basis
direct: dashboard.py:145-191 computes rental_income/expense/net/deposit as OverviewResponse fields. projection.py:6-102 combines assets+liabilities into net worth. AssetSnapshot.breakdown is extensible JSON. Verified: sound.
Rationale
Without net worth integration, travel spending is invisible in the family's financial picture — a family could be steadily eroding net worth through travel without seeing it in their dashboard. The rental mirror pattern means zero new aggregation infrastructure.
Downsides
Travel "float" is conceptually different from rental cash flow (rental is recurring income; travel is episodic spending). The metric may confuse users if not well-labeled. Requires the expense ledger (Idea #3) to be built first.
Confidence: 85% Complexity: Low
#5 Municipal CAFR Annual Cycle — Monthly Rollup + AI Narrative liability-and-stats

Model annual travel statistics on the municipal Comprehensive Annual Financial Report (CAFR) cycle. Extend the daily snapshot generator with a monthly travel rollup job in the scheduler worker: aggregate trip expenses by category, destination, and family member into a monthly summary. The annual report then reads 12 monthly rows instead of 365 daily rows. The dashboard narrative system generates AI-powered year-end travel summaries: "Your family spent 23% more on travel this year, primarily driven by the Japan trip."

Basis
direct: auto_generate_daily_snapshots at snapshot.py:56 is a daily scheduler job. liability_calculator.py:51-88 computes month-by-month amortization schedules. AssetSnapshot.breakdown is extensible JSON Text. Verified: sound.
Rationale
No periodic reporting exists in the codebase. Monthly rollups create a pre-aggregated time series that makes year-over-year comparison, trend detection, and AI narrative generation fast and natural. The "travel fiscal year" concept aligns with how families actually think about travel spending.
Downsides
Introduces a new scheduler job and data model (monthly travel rollup). The rollup job adds complexity to the scheduler worker. AI narrative quality depends on having enough historical data (12+ months).
Confidence: 82% Complexity: Medium
#6 Greedy Debt Simplification for Group Settlement bill-splitting

After a trip's split expenses are tallied, each participant has a net balance (owed or owing). Apply the greedy max-creditor/max-debtor algorithm: repeatedly match the largest debtor with the largest creditor, settle min(|debt|, |credit|), and eliminate one party per iteration. This reduces N participants to at most N-1 transactions. Expose as a one-tap "simplify debts" action. Settlement transactions reuse the CoinTransaction double-entry pattern with a new transaction_type: "split_settle".

Basis
external: Splitwise's debt simplification algorithm (greedy max-creditor/max-debtor matching) — proven at scale with 100M+ users. direct: CoinTransaction double-entry at coin_transactions.py:78-79 with extensible transaction_type string. Verified: sound.
Rationale
Without simplification, a 4-family trip generates up to 12 settlement transactions. With simplification, it reduces to 3. This is the key UX differentiator for the split module — without it, settlement is painful; with it, the module delivers real value over manual spreadsheet tracking.
Downsides
The greedy algorithm is not globally optimal (the problem is NP-hard). For small groups (4-6 families) this is acceptable. Settlement transactions are internal to Numina — actual money transfer still happens externally.
Confidence: 90% Complexity: Low
#7 Travel as Ephemeral Context Overlay (Not a Tab) trip-planning

Challenge the assumption: instead of adding a 5th van-tab, model a "trip" as a temporary context window that overlays the existing FinanceHubPage. When a trip is active (departure within N days or user-pinned), its expenses, bookings, and budget appear as a floating context layer on top of the existing tabs — expenses show inline in the asset list, liabilities show in the liability tab, bookings appear as date-marked cards. The "旅游" entry point is a trip launcher button, not a tab.

Basis
reasoned: Travel is a project that draws on assets and creates temporary liabilities — not a peer category of assets/liabilities. A tab implies permanence for something used episodically. complete_wish already treats travel as an "experience" not an "asset-type". Verifier noted weak (docstring ≠ architectural constraint), but the conceptual reframing remains valid as a design choice.
Rationale
Treating travel as context rather than category keeps the mental model clean and avoids fragmenting the dashboard. A family doesn't "have travel" the way they "have assets" — they go on trips that temporarily affect their financial picture.
Downsides
Contradicts user's literal request for a "旅游 tab". High implementation complexity (overlay context system doesn't exist). May confuse users who expect a dedicated travel management space. The contextual overlay pattern is untested in the codebase.
Confidence: 60% Complexity: High
#8 Receipt-First Expense Entry via import-parse expense-tracking

Invert the expense entry workflow: instead of users manually typing travel expenses, they photograph receipts or forward booking confirmations. The existing import-parse AI skill (which already parses shopping receipts and financial documents via vision) is extended with a travel-receipt document type. The system extracts vendor, amount, currency, date, and category automatically. Users confirm, not create. The expense record is the output of parsing, not the input of a form.

Basis
direct: import-parse SKILL.md already handles "Shopping receipts / purchase invoices → extract purchased items" with vision pipeline + batch-write MCP tool. Extending to travel expenses reuses the same read_file → view_image → structured JSON → batch write architecture.
Rationale
Travel generates the most receipt clutter of any expense category — hotel folios, restaurant bills, transport tickets — all in mixed currencies. Manual entry is the #1 drop-off point for expense trackers. By inverting the workflow from "user creates record" to "system extracts record, user confirms," friction shifts from data entry to data review.
Downsides
Requires the AI agent system to be available (LLM cost per receipt). OCR accuracy varies for handwritten receipts or non-standard formats. Mixed-currency receipt parsing is harder than single-currency. Latency may frustrate users expecting instant capture.
Confidence: 75% Complexity: Medium
