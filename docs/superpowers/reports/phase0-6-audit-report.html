1. Executive Summary

The external MCP token system is substantially implemented with correct security fundamentals: hash-only storage, family-scoped queries, dual-path auth, tool-level authorization, audit logging with redaction, and anomaly detection. However, several spec deviations exist — notably the token prefix length (8 vs spec's 12), missing audit columns (revoked_at/revoked_by), no mcp_anomaly_alerts table (uses notification system instead), and query-param token leakage risk in nginx logs.

118 tests pass (66 unit + 52 integration), migration chain is valid, internal MCP is unaffected, and critical security paths (tenant isolation, synthetic user containment, tool authorization) are verified.

3. Missing / Incorrect Implementations

[P1] SPEC-1: token_prefix length mismatch

Spec vs Implementation

Requirement: token_prefix = Column(String(12))

Current: token_prefix: Mapped[str] = mapped_column(String(8)) at models/family_mcp_token.py:22

Evidence: Migration mcp001token also uses String(8). The code stores first 8 chars of the token (e.g., mcp_ABCD) instead of 12.

Impact: MEDIUM — With 8 base64url chars (~48 bits), birthday collision becomes feasible at ~16M tokens. While hash verification prevents auth bypass, a collision in the POST /messages path (no family_id in URL) could theoretically resolve to the wrong family's token row before hash check fails. The prefix is also used as part of the rate-limit key.

Root cause: Implementation deviated from spec during development.

[P1] SPEC-2: Missing revoked_at / revoked_by columns

Spec vs Implementation

Requirement: revoked_at = Column(DateTime, nullable=True) and revoked_by = Column(SnowflakeID, nullable=True) with FK to User.

Current: Model uses is_active: Mapped[bool] = mapped_column(Boolean, default=True) at models/family_mcp_token.py:31. No record of WHO revoked or WHEN.

Evidence: services/mcp_token.py:190-200 — revoke_token() sets is_active=False but doesn't record revoker or timestamp.

Impact: MEDIUM — Audit trail gap. If a token is compromised and revoked, there's no record of when the revocation occurred or which owner action caused it. This weakens forensic analysis.

Root cause: Implementation chose simpler boolean flag over spec's audit-friendly columns.

[P1] SEC-FE1: Stats page missing owner-only guard (discovered by frontend-auditor)

Authorization Bypass

Requirement: All MCP management endpoints and UI must be owner-only.

Current: MCPStatsPage.vue at route /settings/ai/mcp/stats has NO isOwner check and NO route guard. Any authenticated user (including member role) can access the stats page and see call counts, IP breakdowns, tool usage, and recent activity.

Evidence: frontend/apps/main/src/pages/MCPStatsPage.vue — no isOwner computed, no beforeEnter guard. The backend stats endpoint (ai_mcp_token.py:144) correctly requires require_owner, so API calls will return 403 for non-owners. But the page itself renders for all roles.

Impact: LOW-MEDIUM — Backend enforces owner-only, so the API will return 403 for non-owners who navigate directly. But the page UI renders (empty/error state) for members, which is a UX inconsistency and could leak information if the backend guard is ever weakened.

Root cause: Frontend route was added without owner-only meta/guard.

[P2] SEC-3: Query-param token leakage in nginx access logs

Security Risk

Requirement: "Token in query param will be logged in nginx access logs, application logs, and potentially in tracing/metrics."

Current: The nginx production config (nginx.production.conf) does NOT strip query parameters from the access log for MCP endpoints. The default nginx log format includes $request_uri which contains the full URL including query string.

Evidence: nginx.production.conf:98-103 — no location /api/v1/mcp/public/ block with query stripping. The backend logs only the prefix (8 chars) at WARNING level when query-param auth is used (mcp_public.py:216-219), which is correct.

Impact: MEDIUM — If nginx access logs are enabled (they are by default for the API location), full tokens sent via ?token=mcp_xxx will be persisted in plaintext on disk.

Recommended fix: Add nginx location block for /api/v1/mcp/public/ that strips query params from logs, or recommend Bearer header as the only production-safe auth method.

[P2] P2-AE5: Rate limiting has no dedicated tests

Test Coverage Gap

Requirement: Rate limiting 30 req/min, keyed by (token_prefix, client_ip), fail-open.

Current: Implementation at routers/mcp_public.py:20-44 looks correct but has NO dedicated tests.

Missing tests: boundary (29/30/31), different tokens same IP, window reset, cache unavailable fail-open.

Impact: LOW — Implementation appears correct from code review, but behavior is unverified.

Endpoints: GET /stats, GET /access-logs, GET /tools at routers/ai_mcp_token.py:104,144,160.

Status: Code exists and follows correct patterns (family-scoped, owner-only), but no unit tests verify the SQL queries, pagination, or empty-dataset handling. The stats service (mcp_stats.py) has no test file.

[P2] SEC-FE2: Manage page renders for all roles (metadata exposure)

Information Disclosure

Current: MCPManagePage.vue renders BackendMCPCard for all authenticated roles. Non-owners can see token metadata (token_last4, last_used_at, created_at, allow_external status). Actions (generate, rotate, toggle) are gated by isOwner, but the metadata is exposed.

Impact: LOW — This is information a family member might reasonably know (that MCP is enabled, when it was last used). However, the Issue specifies owner-only management.

[P3] SEC-FE3: Unhandled promise rejections on dialog cancel

Console Pollution

Current: All 3 showConfirmDialog calls in BackendMCPCard.vue (lines 205, 226, 238) lack try/catch. When user clicks Cancel, Vant rejects the promise, producing unhandled promise rejections in the console.

Impact: LOW — Functionally correct (cancel prevents API call), but pollutes console and could trigger global error handlers or error monitoring tools.

4. Spec Deviations (Documented, Not Bugs)

P1-AE1: Model field differences from spec
  • token_last4 — Spec says token_last4, model matches. But spec said last4 in one place and token_last4 in another. Implementation chose token_last4.
  • No external_user_id FK — Spec mentions external_user_id = Column(SnowflakeID, ForeignKey("users.id"), nullable=True). Implementation resolves synthetic user at runtime instead of storing the FK. Functionally equivalent — the synthetic user is always found by (family_id, role=external_token) query.
  • No mcp_anomaly_alerts table — Spec mentions this table. Implementation uses the notification system's reminders table via ensure_reminder(). This is architecturally correct — alerts appear in the user's notification inbox.
  • No unique constraint on (family_id, name) — Spec requires UniqueConstraint("family_id", "name"). Implementation only has a composite index (not unique). Since names are user-provided and only one active token exists per family at a time, this is a minor gap.
  • No name field at all — Spec requires name = Column(String(100), nullable=False). Implementation has no name column. Since only one active token per family is supported, the name field (for labeling multiple tokens) is unused.
  • No token_prefix in access logs — Spec mentions token_prefix in mcp_access_logs. Implementation uses token_id FK instead. Functionally equivalent (can join to get prefix), but differs from spec.
Section 3: Token plaintext display contradiction

The issue contains contradictory requirements:

  • Section 5: "眼睛按钮显示完整 Token，10 秒后重新 mask"
  • Section 7: "不保存明文，完整 Token 只在生成时返回一次"

Resolution: Implementation chose the one-time-secret model. The plaintext is stored in the frontend's plaintext ref (in-memory only). The eye toggle reveals it from memory for 10 seconds, then re-masks. After page refresh, only the masked version is available. This is the MORE SECURE interpretation and is correct.

Evidence: BackendMCPCard.vue:172-181 — displayToken() toggles between plaintext.value and maskedToken() with 10s auto-remask.
