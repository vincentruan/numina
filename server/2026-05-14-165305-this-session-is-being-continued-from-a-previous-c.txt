  ---
  Key Findings by Principle

  Action Parity (29%) — The 8 existing agent capabilities are all read-only
  analysis tools (report, alerts, disposal, liability, allocation, spending
  leak, time machine, chat). The entire write surface — asset CRUD, liability
  CRUD, chore management, child wishes, coin rewards, family management — has no
   agent coverage. The agent can analyze but cannot act.

  CRUD Completeness (18%) — Only 9 of 49 entities have full CRUD. The 9 that do
  (Asset, Liability, Wish, Category, Tag, Chore, Child, BlindBoxGift,
  NotificationChannel) are the right ones to prioritize. The remaining 40 are
  mostly system/audit records where read-only is intentional and correct.

  Context Injection (42%) — The most impactful gap: assets and members are
  hardcoded to [] in orchestrator._build_context()
  (server/apps/agent/services/orchestrator.py:642-643). The LLM receives
  dashboard aggregates but cannot see individual assets by name, type, or value.
   This limits the quality of every analysis capability.

  Tools as Primitives (50%) — The 8 primitive services (PolicyGuard,
  AuditLogger, SessionStore, PIIRedactor, etc.) are well-designed. The 8
  workflow services embed business logic that should live in routers or schema
  modules. The Orchestrator class is the biggest offender — it encodes the
  entire dispatch pipeline as a 28KB class.

  UI Integration (67%) — Chat streaming and AI report WebSocket are excellent.
  The gap is asset mutations: when the agent (or any user)
  creates/updates/deletes an asset, other family members don't see it until
  manual refresh. fire_notification() is already used for wishes/chores/coins —
  the same pattern just needs to be applied to asset endpoints.

  Capability Discovery (71%) — Strong foundation. Missing: slash commands and
  in-app help documentation. The /capabilities endpoint and AIHubPage feature
  grid already provide the data; it's a matter of surfacing it in more places.

  Prompt-Native (56%) — Disposal scoring (FREQ_SCORE dict, hardcoded cost/age
  thresholds) and aging alert thresholds (180/365 days) are the clearest
  candidates for externalization. These are tuning parameters that should not
  require a code deploy to change.
